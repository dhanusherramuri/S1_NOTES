stm32f103 workspace notes

three-thread-blink_hse, explained

The same three LED tasks as three-thread-blink, run at 72 MHz off the external crystal instead of the default 8 MHz internal oscillator, with the idle task actually asleep between ticks instead of spinning.

1

What's different

Three files exist in this project; everything else - startup_stm32f103.s, stm32f103.ld, common.mk - is untouched, shared with every other project in the workspace.

FileChanged from three-thread-blink
MakefileOnly PROJECT's name - the build rules are identical
FreeRTOSConfig.hconfigCPU_CLOCK_HZ is 72 MHz, not 8 MHz; configUSE_IDLE_HOOK is now 1
main.cAdds clock_setup_hse_pll_72mhz() and vApplicationIdleHook(); the three LED tasks themselves are byte-for-byte the same

FreeRTOSConfig.h

three-thread-blink_hse/FreeRTOSConfig.h (trimmed)

// this MUST match whatever SYSCLK actually ends up at
#define configCPU_CLOCK_HZ              72000000UL
#define configTICK_RATE_HZ              1000
#define configTOTAL_HEAP_SIZE           (4 * 1024)

#define configUSE_IDLE_HOOK             1   // -> vApplicationIdleHook() sleeps the CPU
#define configUSE_TICK_HOOK             0

// bridges startup.s's vector names to FreeRTOS's own (unchanged)
#define vPortSVCHandler      SVC_Handler
#define xPortPendSVHandler   PendSV_Handler
#define xPortSysTickHandler  SysTick_Handler

Two lines actually differ from three-thread-blink's config, and both matter more than their size suggests.

  • configCPU_CLOCK_HZ - not read from hardware, ever. It's a number FreeRTOS trusts completely, and it feeds straight into the SysTick reload calculation inside the port layer: (configCPU_CLOCK_HZ / configTICK_RATE_HZ) - 1. Change the clock without changing this constant and every vTaskDelay() in the program silently runs 9× too fast or too slow.
  • configUSE_IDLE_HOOK - flips on the single call to vApplicationIdleHook() that tasks.c's idle task makes every time it runs. Without this, the function in main.c would compile fine and simply never be called.
4

main.c

Structurally the same file as three-thread-blink/main.c - the led_task_args_t struct, gpio_output_init(), and led_task() are unchanged. Two things are added: a clock-configuration function called once at the very top of main(), and an idle hook at the bottom.

three-thread-blink_hse/main.c - main() and the two new pieces (trimmed)

static void clock_setup_hse_pll_72mhz(void)
{
    /* five steps - see the walkthrough below */
}

int main(void)
{
    clock_setup_hse_pll_72mhz();                 // (1) do this FIRST

    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_IOPCEN;
    gpio_output_init(led_a.port, led_a.pin);
    gpio_output_init(led_b.port, led_b.pin);
    gpio_output_init(led_c.port, led_c.pin);

    xTaskCreate(led_task, "led_1s", configMINIMAL_STACK_SIZE, (void *)&led_a, tskIDLE_PRIORITY + 1, NULL);
    xTaskCreate(led_task, "led_2s", configMINIMAL_STACK_SIZE, (void *)&led_b, tskIDLE_PRIORITY + 1, NULL);
    xTaskCreate(led_task, "led_3s", configMINIMAL_STACK_SIZE, (void *)&led_c, tskIDLE_PRIORITY + 1, NULL);

    vTaskStartScheduler();
    for (;;) { }
}

void vApplicationIdleHook(void)              // (2) called every idle-task run
{
    __asm volatile ("wfi");
}

Notice where clock_setup_hse_pll_72mhz() is called: before anything else, including the GPIO clock-enable. Nothing downstream can safely assume a clock speed until this function has either finished switching to 72 MHz or given up and left the chip on HSI - the two deep dives below cover each addition in full.

5

Clock setup, step by step

RM0008 §7.3 is the source for this whole sequence. Five steps, each one gated on the previous one actually finishing - there's no way to skip ahead, because each step's register write is only valid once the one before it has taken effect in hardware.

Why this exact order

  • Flash latency before the switch, not after. Step 2 happens while the core is still running at 8 MHz - slow enough that flash keeps up regardless of the latency setting. If the clock rose to 72 MHz first, the very next instruction fetch could already be too fast for 0-wait-state flash to service correctly.
  • PLL configuration before PLL enable. RCC_CFGR's PLLSRC/PLLXTPRE/PLLMUL fields are only permitted to change while the PLL is off - RM0008 is explicit about this. Step 3 sets them; step 4 is the first point PLLON is touched.
  • SW is the last thing touched. Everything before step 5 can be undone or was never visible to the running program - the CPU is still executing at the original 8 MHz HSI rate right up until the SW write actually commits.
6

The sleeping idle task

FreeRTOS always creates one extra task you didn't ask for: the idle task, priority 0, the lowest in the system. It runs whenever - and only whenever - none of your own tasks are Ready. In three-thread-blink, that idle task's body is effectively an empty loop. Here, it does one thing differently.

three-thread-blink_hse/main.c - vApplicationIdleHook

void vApplicationIdleHook(void)
{
    __asm volatile ("wfi");   // Wait For Interrupt - halts the core
}

wfi is a single Cortex-M3 instruction, not a library call - it needs no CMSIS intrinsic, just the inline assembly line above. Architecturally, if an interrupt is already pending the instant wfi executes, the core is guaranteed to fall straight through instead of sleeping through a missed event - which is what makes it safe to call unconditionally here, with no extra interrupt-masking logic needed around it.

Why not full tickless idle. FreeRTOS's configUSE_TICKLESS_IDLE goes further - it stops SysTick entirely during long idle stretches and reprograms it to fire exactly when the next task is due, so the core can sleep for seconds instead of milliseconds. That's real additional complexity: computing the next wake time, handling the race between "decide to sleep" and "an interrupt arrives," correcting the tick count on wake. This project takes the simpler win instead - the tick keeps running, so there's no race to get wrong, and the core still spends the overwhelming majority of every millisecond genuinely asleep rather than spinning.

8

Build and flash

  1. FreeRTOS already cloned? This project shares the same ../FreeRTOS/ clone as three-thread-blink - if you've already built that project in this workspace, nothing more to fetch. Otherwise: git clone --depth 1 https://github.com/FreeRTOS/FreeRTOS-Kernel.git FreeRTOS from inside stm32f103/.
  2. Build. cd three-thread-blink_hse && make - produces build/three-thread-blink_hse.elf/.bin/.hex and prints a size summary.
  3. Flash. make flash - st-flash write build/three-thread-blink_hse.bin 0x8000000.
  4. Confirm. Same three periods as before - PC13 at 1 s, PA0 at 2 s, PA1 at 3 s - but now timed off a crystal instead of the internal RC oscillator, and with the core genuinely idle between ticks. If your board doesn't have a fitted HSE crystal, the LEDs still blink at the correct rate regardless - clock_setup_hse_pll_72mhz() silently falls back to HSI rather than hanging, and FreeRTOS was never told the clock actually changed... which is exactly why a fitted crystal matters here more than in most projects.

One real hazard. If your board's crystal is missing or unsoldered, this function returns having done nothing - the chip is still on 8 MHz HSI - but configCPU_CLOCK_HZ in FreeRTOSConfig.h still says 72000000UL. FreeRTOS will program a SysTick reload value nine times too large, and every vTaskDelay() period in the program will silently run nine times too slow. The LEDs will still blink, just at roughly 9 s, 18 s, and 27 s instead of 1/2/3 - worth knowing if the timing ever looks wrong on real hardware.
