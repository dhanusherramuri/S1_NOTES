Priority Inversion — Demo, Gantt, and Fix

A program that deliberately triggers the classic priority inversion on a Bluepill, the Gantt chart of what actually executes on the core, and the one-line change that fixes it.

The three tasks

hardware and priorities

TaskPriorityPinMechanism
Task1 — task1_highHIGH (3)PA0 — external LEDTakes binary semaphore, blinks 500 ms on / 500 ms off, gives semaphore
Task2 — task2_lowLOW (1)PA1 — external LEDTakes binary semaphore, blinks 500 ms on / 500 ms off, gives semaphore
Task3 — task3_medMED (2)PC13 — onboard LEDNo semaphore. Busy-waits 500 ms × 5 cycles, then sleeps 500 ms once

PA0 and PA1 are collectively protected by a binary semaphore — not a mutex. The distinction is exactly what makes the inversion happen: a FreeRTOS mutex carries priority inheritance, which would automatically prevent the inversion. A binary semaphore has zero awareness of task priorities, so the problem plays out in full.

The code

priority-inversion/main.c — the three task functions and main()

/* resource protection: binary semaphore, NOT a mutex */
static SemaphoreHandle_t xGpioABinarySem;

/* busy-wait: spins on a tick counter, never yields */
static volatile uint32_t g_ticks = 0;
void vApplicationTickHook(void) { g_ticks++; }

static void busy_wait_ms(uint32_t ms)
{
    uint32_t start = g_ticks;
    while ((g_ticks - start) < ms) { }   /* spin */
}

/* Task1 HIGH — blinks PA0 */
static void task1_high(void *pv)
{
    vTaskDelay(pdMS_TO_TICKS(10));   /* small head-start lets Task2 grab sem first */
    for (;;) {
        xSemaphoreTake(xGpioABinarySem, portMAX_DELAY);
        GPIOA->ODR |=  (1U << 0);   vTaskDelay(pdMS_TO_TICKS(500));
        GPIOA->ODR &= ~(1U << 0);   vTaskDelay(pdMS_TO_TICKS(500));
        xSemaphoreGive(xGpioABinarySem);
    }
}

/* Task2 LOW — blinks PA1 */
static void task2_low(void *pv)
{
    for (;;) {
        xSemaphoreTake(xGpioABinarySem, portMAX_DELAY);   /* takes sem at T=0 */
        GPIOA->ODR |=  (1U << 1);   vTaskDelay(pdMS_TO_TICKS(500));
        GPIOA->ODR &= ~(1U << 1);   vTaskDelay(pdMS_TO_TICKS(500));
        xSemaphoreGive(xGpioABinarySem);                   /* releases sem at T=1000 */
    }
}

/* Task3 MED — blinks PC13, busy-waits 5×500 ms, then sleeps once */
static void task3_med(void *pv)
{
    for (;;) {
        for (uint32_t i = 0; i < 5; i++) {
            GPIOC->ODR ^= (1U << 13);
            busy_wait_ms(500);   /* SPIN — never yields — starves Task2 */
        }
        vTaskDelay(pdMS_TO_TICKS(500));   /* only yields ONCE per outer loop */
    }
}

int main(void)
{
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_IOPCEN;
    gpio_output_init(GPIOA, 0);
    gpio_output_init(GPIOA, 1);
    gpio_output_init(GPIOC, 13);

    xGpioABinarySem = xSemaphoreCreateBinary();
    xSemaphoreGive(xGpioABinarySem);   /* start it available */

    xTaskCreate(task1_high, "T1_HIGH", configMINIMAL_STACK_SIZE, NULL, PRIO_HIGH, NULL);
    xTaskCreate(task2_low,  "T2_LOW",  configMINIMAL_STACK_SIZE, NULL, PRIO_LOW,  NULL);
    xTaskCreate(task3_med,  "T3_MED",  configMINIMAL_STACK_SIZE, NULL, PRIO_MED,  NULL);

    vTaskStartScheduler();
    for (;;) {}
}

What happens — the inversion sequence

step by step, before looking at the gantt

Five events, each one setting up the next:

  1. T = 0 ms. Task2 (LOW) runs first — Task1 has a deliberate 10 ms head-start delay that gives Task2 time to call xSemaphoreTake() and acquire the semaphore. Task2 then calls vTaskDelay(500) for the PA1-on phase. Task2 is now Blocked.
  2. T ≈ 0 ms. Task3 (MED) wakes up. MED > LOW, so the scheduler picks Task3 the instant Task2 blocks. Task3 enters its outer loop and calls busy_wait_ms(500) — a pure spin on a tick counter. It never calls vTaskDelay(), so it stays in Running/Ready the entire 500 ms.
  3. T ≈ 500 ms. Task1 (HIGH) wakes up (its 10 ms head-start has long expired). Task1 calls xSemaphoreTake(). The semaphore is held by Task2. Task1 blocks — a HIGH priority task is now waiting on a LOW priority task.
  4. T = 500 ms → T = 2500 ms. Task3 busy-waits through its remaining 4 cycles. Task2 (LOW) cannot run because Task3 (MED) is always ahead of it on the ready list. Task1 (HIGH) cannot run because the semaphore isn't available. The CPU belongs entirely to Task3 — the lowest-priority blocked task has become the de facto gatekeeper for the highest-priority running task.
  5. T ≈ 2500 ms. Task3 finally calls vTaskDelay(500). Task3 is now Blocked. Task2 (LOW) is now the highest-priority Ready task. Task2 runs, finishes its PA1-off phase, calls xSemaphoreGive(). Task1 unblocks immediately — it has been waiting ≈2000 ms for a semaphore it couldn't get because a medium-priority task was in the way.

Gantt chart — priority inversion (binary semaphore)

What the Gantt makes visible: Task3 (MED) never touches the semaphore, never interacts with Task1 or Task2 directly — and yet it is the effective cause of Task1's 2000 ms delay. That indirection is what makes priority inversion hard to spot in real systems: the task that suffers (Task1) and the task that causes the suffering (Task3) have no direct relationship at all.

The fix — replace binary semaphore with a mutex

one line changed, priority inheritance enabled

A FreeRTOS mutex created with xSemaphoreCreateMutex() carries a priority inheritance mechanism built into the kernel. When a task attempts to take the mutex and blocks, the kernel checks the priority of the waiter. If it is higher than the current holder, the holder's priority is temporarily raised to match — so it can run, finish, and release the mutex as soon as the CPU is available, rather than being stuck behind every medium-priority task in the system.

priority-inversion/main.c — the one-line fix

/* BEFORE: binary semaphore — no priority awareness */
xGpioABinarySem = xSemaphoreCreateBinary();
xSemaphoreGive(xGpioABinarySem);   /* must pre-give a binary semaphore */

/* AFTER: mutex — priority inheritance included */
xGpioABinarySem = xSemaphoreCreateMutex();
/* a mutex starts available — no pre-give needed */

Also drop the handle rename. Rename xGpioABinarySem to xGpioAMutex in your own source for clarity — the type is the same SemaphoreHandle_t, the APIs (xSemaphoreTake / xSemaphoreGive) are the same, the mutex just adds the inheritance behaviour under the hood.

Gantt chart — with priority inheritance (mutex)

How priority inheritance works, precisely

Five kernel actions, triggered automatically the moment xSemaphoreTake() blocks on a held mutex:

  1. Task1 (HIGH) calls xSemaphoreTake() and finds the mutex is held by Task2 (LOW). It cannot proceed.
  2. The kernel reads the priority of the blocked waiter (Task1 = HIGH = 3) and compares it with the mutex holder's current priority (Task2 = LOW = 1).
  3. The kernel raises Task2's priority to 3 — Task1's level. Task2 is now effectively a HIGH priority task in the scheduler's view.
  4. Task2 (now boosted to HIGH) preempts Task3 (MED = 2) because 3 > 2. Task2 finishes its blink, calls xSemaphoreGive().
  5. The mutex is given, Task1 unblocks, Task2's priority is restored to LOW (1). The kernel undoes the temporary boost at the exact moment ownership transfers.

Priority inheritance doesn't remove the wait entirely — Task1 still has to wait for Task2 to finish its current blink operation. What it removes is the unbounded wait: the inversion window is now bounded by Task2's own work, not by however long Task3 decides to spin.
