stm32f103 workspace notes

The stm32f103 Build System, Explained

A walk through every file in stm32f103.zip - what it does, why it's shaped the way it is, and where in the reference manuals the numbers came from.

1

Overall layout

One root directory holds everything: FreeRTOS's source, the pieces every project shares, and each project in its own folder.

Two projects ship in the zip. led-blink is deliberately the simplest thing that can run on the board - one file, no RTOS, no library beyond what's in common/. three-thread-blink is the same board with FreeRTOS linked in directly from source, running three independent tasks.

2

Inside common/

Four files, and both projects use every one of them unmodified. This is the only code in the whole workspace that talks to hardware registers or the linker directly - everything in a project folder is ordinary C.

startup_stm32f103.s

Two jobs: lay out the interrupt vector table at the very start of flash, and provide Reset_Handler - the first code the CPU ever runs.

common/startup_stm32f103.s - vector table (excerpt)

g_pfnVectorTable:
    .word _estack               ; initial stack pointer - from the linker script
    .word Reset_Handler         ; entry 1: where execution begins
    .word NMI_Handler
    .word HardFault_Handler
    ; ... core ARMv7-M exceptions ...
    .word SVC_Handler
    .word DebugMon_Handler
    .word PendSV_Handler
    .word SysTick_Handler
    ; --- STM32F103 peripheral interrupts, RM0008 Table 63 ---
    .word WWDG_IRQHandler        ; IRQ 0
    .word PVD_IRQHandler         ; IRQ 1
    ; ... through IRQ 42 (USBWakeUp) ...

RM0008 Table 63 is exactly where that peripheral ordering comes from - the vector table is positional, so TIM2_IRQHandler has to sit at word offset 28 from the table's start or the hardware will jump to the wrong place the moment TIM2 fires. The first sixteen entries (stack pointer through SysTick_Handler) aren't STM32-specific at all - they're defined by the ARMv7-M architecture itself and are identical on every Cortex-M3 part from any vendor.

Every one of those handler names is declared .weak, aliased to a do-nothing Default_Handler:

common/startup_stm32f103.s - Reset_Handler + weak defaults

Reset_Handler:
    ; copy .data's initial values out of flash into RAM
    ldr r0, =_sidata
    ldr r1, =_sdata
    ldr r2, =_edata
copy_data_loop:
    cmp r1, r2
    bcs copy_data_done
    ldr r3, [r0], #4
    str r3, [r1], #4
    b copy_data_loop
copy_data_done:

    ; zero-fill .bss
    ldr r1, =_sbss
    ldr r2, =_ebss
    movs r3, #0
zero_bss_loop:
    cmp r1, r2
    bcs zero_bss_done
    str r3, [r1], #4
    b zero_bss_loop
zero_bss_done:

    bl main
loop_forever:
    b loop_forever

Default_Handler:
    b .                          ; nothing plugged in? spin here, forever

    .macro def_weak name
    .weak \name
    .thumb_set \name, Default_Handler
    .endm
    def_weak NMI_Handler
    def_weak SVC_Handler
    def_weak PendSV_Handler
    def_weak SysTick_Handler
    ; ... one def_weak per vector table entry ...

That weakness is what lets the same file serve both projects. led-blink defines its own SysTick_Handler and nothing else - everything else quietly falls back to Default_Handler. three-thread-blink pulls in FreeRTOS's port layer, which supplies strong definitions of SVC_Handler, PendSV_Handler, and SysTick_Handler that override the weak ones automatically at link time. startup_stm32f103.s itself never changes - and never needs to know FreeRTOS exists.

stm32f103.ld

Tells the linker where flash and RAM actually are, and how to lay out the sections that come out of compilation.

common/stm32f103.ld

ENTRY(Reset_Handler)

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}

_estack = ORIGIN(RAM) + LENGTH(RAM);   ; top of RAM = initial SP

SECTIONS
{
    .isr_vector : { KEEP(*(.isr_vector)) } >FLASH
    .text       : { *(.text*) *(.rodata*) } >FLASH

    .data :
    {
        _sdata = .;
        *(.data*)
        _edata = .;
    } >RAM AT> FLASH                    ; lives in RAM, initial values stored in FLASH

    _sidata = LOADADDR(.data);          ; where Reset_Handler copies FROM

    .bss : { _sbss = .; *(.bss*) *(COMMON) _ebss = .; } >RAM
}

The 64K / 20K figures are the STM32F103C8T6 datasheet's numbers for this specific part - not something derived from the reference manual, which covers the whole F101/102/103/105/107 family across many flash/RAM sizes. Every symbol with a leading underscore here (_estack, _sidata, _sdata, _edata, _sbss, _ebss) is what Reset_Handler, above, reads to do its copy-and-zero work - the startup file and the linker script are two halves of the same mechanism, and they agree on these names by convention, not by any automatic check.

stm32f103_regs.h

The only register definitions anywhere in this workspace - just enough to drive what these two projects actually touch.

PeripheralBase addressSource
RCC0x4002​1000RM0008 §7 Reset and Clock Control registers
GPIOA / B / C0x4001​0800 / 0C00 / 1000RM0008 §9 General-purpose I/O, the F1 CRL/CRH style
SysTick0xE000​E010ARMv7-M Architecture Reference Manual - a core peripheral, same address on every Cortex-M3

The GPIO layout is worth calling out because it trips people up coming from newer STM32 families: F1 doesn't have the single MODER register later families use. Each pin gets a 4-bit field - two bits MODE, two bits CNF - split across two registers, pins 0-7 in CRL and pins 8-15 in CRH. That's exactly what GPIO_CNF_MODE_OUTPUT_PP_2MHZ (0x2) encodes, and why the code you'll see in both projects has to pick CRL or CRH based on which half the pin number falls into.

common.mk

Not hardware-facing at all - this is the actual build logic, and it's the same for every project regardless of whether FreeRTOS is involved.

common/common.mk (trimmed)

MCU_FLAGS = -mcpu=cortex-m3 -mthumb

CFLAGS  = $(MCU_FLAGS) -std=gnu11 -Os -g3 -Wall -Wextra
CFLAGS += -ffunction-sections -fdata-sections
CFLAGS += -I$(COMMON_DIR)
CFLAGS += $(EXTRA_CFLAGS)              ; a project adds its own include paths here

LDFLAGS  = $(MCU_FLAGS)
LDFLAGS += --specs=nano.specs --specs=nosys.specs
LDFLAGS += -nostartfiles -Wl,--gc-sections
LDFLAGS += -T$(LDSCRIPT)

ALLSRCS := $(SRCS) $(STARTUP)          ; every project gets startup.s appended automatically
OBJS    := $(addprefix $(BUILD_DIR)/,$(notdir $(ALLSRCS)))
OBJS    := $(OBJS:.c=.o)
OBJS    := $(OBJS:.s=.o)
vpath %.c $(sort $(dir $(ALLSRCS)))    ; lets make find sources wherever they actually live
vpath %.s $(sort $(dir $(ALLSRCS)))

$(BUILD_DIR)/%.o: %.c | $(BUILD_DIR)
	$(CC) $(CFLAGS) -MMD -MP -c $< -o $@

$(BUILD_DIR)/$(PROJECT).elf: $(OBJS)
	$(CC) $(OBJS) $(LDFLAGS) -o $@

A project's own Makefile only ever sets three things - PROJECT, SRCS, and optionally EXTRA_CFLAGS - then includes this file. The vpath lines are what make that work even when SRCS points at files deep inside FreeRTOS/: object files always land in this project's own build/, named by basename only, regardless of how far away the source actually lives.

led-blink/

No RTOS, no heap, one source file. The onboard LED on PC13 toggles every 500 ms, timed by polling a millisecond counter that SysTick increments in the background.

Makefile

led-blink/Makefile - complete

ROOT_DIR := $(abspath $(dir $(lastword $(MAKEFILE_LIST)))..)
PROJECT  := led-blink

SRCS := main.c

include $(ROOT_DIR)/common/common.mk

That's the entire file. ROOT_DIR is computed from the Makefile's own path rather than assumed, so it's correct whether you cd into led-blink/ and run make, or run make -C led-blink from the workspace root.

main.c

led-blink/main.c - complete

#include <stdint.h>
#include "stm32f103_regs.h"

static volatile uint32_t g_msticks;

void SysTick_Handler(void)
{
    g_msticks++;                                // (1) fires 1000x/sec, see below
}

static void delay_ms(uint32_t ms)
{
    uint32_t target = g_msticks + ms;
    while (g_msticks < target) { }               // (2) busy-wait, nothing else runs
}

int main(void)
{
    RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;         // (3) power up GPIOC

    GPIOC->CRH &= ~(0xFU << 20);                // (4) clear PC13's 4-bit field
    GPIOC->CRH |=  (GPIO_CNF_MODE_OUTPUT_PP_2MHZ << 20);  // output, push-pull, 2 MHz

    SYSTICK->LOAD = (8000000U / 1000U) - 1U;    // (5) 8 MHz HSI / 1000 Hz tick
    SYSTICK->VAL  = 0;
    SYSTICK->CTRL = SYSTICK_CTRL_CLKSOURCE
                  | SYSTICK_CTRL_TICKINT
                  | SYSTICK_CTRL_ENABLE;

    for (;;) {
        GPIOC->ODR ^= (1U << 13);                // (6) toggle PC13
        delay_ms(500);
    }
}
  1. The tick source. SysTick_Handler overrides the weak default in startup_stm32f103.s by name alone - nothing links it explicitly. It just increments a counter; that's the entire ISR.
  2. The delay. A plain spin-loop on that counter. No sleep, no low-power wait - the core is busy the whole 500 ms, which is fine here and would be the first thing to fix in anything power-sensitive.
  3. Clocking on the peripheral. RM0008 §7.3.7 - RCC_APB2ENR, bit 4 (IOPCEN). Every GPIO port is clock-gated at reset; nothing on it responds until this bit is set.
  4. Pin configuration. RM0008 §9.2.2 - GPIOx_CRH covers pins 8-15, four bits each. PC13's field sits at bits 20-23 ((13-8)×4), which is exactly why the code shifts by 20.
  5. Timer setup. ARMv7-M Architecture Reference Manual, SysTick. LOAD is a count-down-from value, so 8,000,000 / 1000 - 1 gives a reload that fires once per millisecond at the default 8 MHz HSI clock this whole workspace assumes (no PLL is configured anywhere).
  6. The visible effect. A read-modify-write XOR on ODR. PC13 is wired active-low on the Bluepill, so this still blinks correctly - XOR doesn't care which polarity is "on."

Build and flash

  1. Build. cd led-blink && make - produces build/led-blink.elf, .bin, and .hex, and prints a size summary. No FreeRTOS clone needed for this one.
  2. Flash. make flash, which runs st-flash write build/led-blink.bin 0x8000000 against an ST-Link. If you don't have st-flash, any tool that writes a raw binary to 0x08000000 works identically - OpenOCD, or the .hex via a different programmer.
  3. Confirm. The onboard LED should start blinking roughly twice a second the moment the write finishes and the board resets.

three-thread-blink/

Same board, same register header, same startup file and linker script - the only thing that changes is that FreeRTOS's own source now sits in the build, and three tasks run instead of one main() loop.

Makefile

three-thread-blink/Makefile - complete

ROOT_DIR     := $(abspath $(dir $(lastword $(MAKEFILE_LIST)))..)
PROJECT      := three-thread-blink

FREERTOS_DIR := $(ROOT_DIR)/FreeRTOS

SRCS := main.c
SRCS += $(FREERTOS_DIR)/tasks.c
SRCS += $(FREERTOS_DIR)/list.c
SRCS += $(FREERTOS_DIR)/queue.c
SRCS += $(FREERTOS_DIR)/portable/GCC/ARM_CM3/port.c
SRCS += $(FREERTOS_DIR)/portable/MemMang/heap_4.c
# timers.c intentionally omitted - configUSE_TIMERS is 0 below

EXTRA_CFLAGS := -I$(FREERTOS_DIR)/include
EXTRA_CFLAGS += -I$(FREERTOS_DIR)/portable/GCC/ARM_CM3
EXTRA_CFLAGS += -I.

include $(ROOT_DIR)/common/common.mk

Five extra source files, in total: the scheduler core (tasks.c), the linked-list implementation the ready/delayed lists are built from (list.c), queues/semaphores (queue.c), the Cortex-M3 port layer (port.c), and one heap implementation (heap_4.c). EXTRA_CFLAGS adds two FreeRTOS include directories plus -I., the last of which is what lets port.c find this project's own FreeRTOSConfig.h - FreeRTOS has no fixed idea where that file lives; it's found purely through the include path.

FreeRTOSConfig.h

three-thread-blink/FreeRTOSConfig.h (trimmed)

// no PLL is configured anywhere in this workspace - must match reality
#define configCPU_CLOCK_HZ              8000000UL
#define configTICK_RATE_HZ              1000
#define configMAX_PRIORITIES            5
#define configTOTAL_HEAP_SIZE           (4 * 1024)   // Bluepill: 20K RAM total
#define configCHECK_FOR_STACK_OVERFLOW  2

// Cortex-M3 NVIC priority config (ARM_CM3 port)
#define configPRIO_BITS                 4
#define configKERNEL_INTERRUPT_PRIORITY \
    (configLIBRARY_LOWEST_INTERRUPT_PRIORITY << (8 - configPRIO_BITS))

// bridges this project's startup.s vector names to FreeRTOS's own
#define vPortSVCHandler      SVC_Handler
#define xPortPendSVHandler   PendSV_Handler
#define xPortSysTickHandler  SysTick_Handler

configCPU_CLOCK_HZ is the one value most likely to bite you if this workspace is ever extended to run at 72 MHz via the PLL - it's a plain number FreeRTOS trusts completely, not something it reads from hardware. configPRIO_BITS is 4 because that's how many priority bits the STM32F1's NVIC actually implements in silicon; getting this wrong doesn't fail to compile, it just makes priority-based interrupt masking silently target the wrong bits. And the last three lines are the exact mechanism this workspace uses to connect startup_stm32f103.s's generic, FreeRTOS-agnostic vector table to FreeRTOS's real handlers - the preprocessor renames port.c's functions to the CMSIS-style names the vector table already expects, so the weak defaults in startup.s get overridden automatically at link time.

main.c

three-thread-blink/main.c - complete

#include "stm32f103_regs.h"
#include "FreeRTOS.h"
#include "task.h"

typedef struct {
    GPIO_TypeDef *port;
    uint32_t      pin;
    uint32_t      period_ms;
} led_task_args_t;

static const led_task_args_t led_a = { GPIOC, 13, 1000 };  // onboard LED
static const led_task_args_t led_b = { GPIOA, 0,  2000 };  // external
static const led_task_args_t led_c = { GPIOA, 1,  3000 };  // external

static void gpio_output_init(GPIO_TypeDef *port, uint32_t pin)
{
    volatile uint32_t *cr = (pin < 8) ? &port->CRL : &port->CRH;
    uint32_t shift = (pin % 8U) * 4U;
    *cr &= ~(0xFU << shift);
    *cr |=  (GPIO_CNF_MODE_OUTPUT_PP_2MHZ << shift);
}

static void led_task(void *pvParameters)
{
    const led_task_args_t *args = (const led_task_args_t *)pvParameters;
    for (;;) {
        args->port->ODR ^= (1U << args->pin);
        vTaskDelay(pdMS_TO_TICKS(args->period_ms));      // Blocked, not spinning
    }
}

int main(void)
{
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_IOPCEN;

    gpio_output_init(led_a.port, led_a.pin);
    gpio_output_init(led_b.port, led_b.pin);
    gpio_output_init(led_c.port, led_c.pin);

    xTaskCreate(led_task, "led_1s", configMINIMAL_STACK_SIZE, (void *)&led_a, tskIDLE_PRIORITY + 1, NULL);
    xTaskCreate(led_task, "led_2s", configMINIMAL_STACK_SIZE, (void *)&led_b, tskIDLE_PRIORITY + 1, NULL);
    xTaskCreate(led_task, "led_3s", configMINIMAL_STACK_SIZE, (void *)&led_c, tskIDLE_PRIORITY + 1, NULL);

    vTaskStartScheduler();       // never returns unless setup failed
    for (;;) { }
}

// required: configCHECK_FOR_STACK_OVERFLOW is 2
void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName)
{
    (void)xTask; (void)pcTaskName;
    for (;;) { }
}

One function, led_task, runs three times with three different arguments - the same pattern as passing a struct pointer to a pthread in any hosted OS. gpio_output_init reuses the exact CRL/CRH logic from led-blink, generalized to pick the right register from the pin number. The one behavioral difference from led-blink that matters most: vTaskDelay puts the calling task into the Blocked state rather than spinning, so the other two tasks (and the idle task) get the core while any one of them is waiting out its period.

PC13 is the only LED actually on the board - PA0 and PA1 need an external LED and a current-limiting resistor (around 330 Ω) to ground each, or you can point led_b/led_c at GPIOC, 13 too and watch all three periods XOR the one onboard LED instead.

Compiling and linking with FreeRTOS

Nothing here is conceptually different from any other multi-file C build - it's worth seeing laid out once, though, since it's the same shape every time FreeRTOS gets linked into a project like this one.

Build and flash

  1. Get FreeRTOS. This project's SRCS point at ../FreeRTOS/..., which isn't in the zip - clone it once at the workspace root: git clone --depth 1 https://github.com/FreeRTOS/FreeRTOS-Kernel.git FreeRTOS (run from inside stm32f103/).
  2. Build. cd three-thread-blink && make. This compiles all seven sources shown above and links them into build/three-thread-blink.elf/.bin/.hex, then prints a size summary - expect a few KB of flash and a few KB of RAM, comfortably inside the F103C8's 64K/20K.
  3. Flash. make flash - identical mechanism to led-blink, st-flash write build/three-thread-blink.bin 0x8000000.
  4. Confirm. PC13 blinks once a second on its own; wire up PA0/PA1 (or repoint them at PC13, see above) to see the 2 s and 3 s tasks running independently of it.

If it doesn't link. The most common first-time failure here is fatal error: FreeRTOSConfig.h: No such file or directory from inside port.c - that means -I. isn't reaching the compiler, usually because make was run from somewhere other than three-thread-blink/ itself. The second most common is an undefined reference to something in FreeRTOS/ - almost always means the clone in step 1 didn't happen, or landed in the wrong place.
