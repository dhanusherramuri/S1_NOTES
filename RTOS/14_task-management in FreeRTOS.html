Task Management in FreeRTOS

A task is nothing exotic - a C function, a private stack, and one small struct the scheduler uses to keep track of it. Everything below is really just different views of that one idea.

1  A task in memory

Creating a task with xTaskCreate() doesn't carve out a new address space - FreeRTOS has no MMU to do that with. It hands the new task exactly one thing that's genuinely its own: a stack. Everything else - the code, the globals, the heap those xTaskCreate() calls come out of - is one shared region every task in the system reads and writes equally.

The trade being made here is the same one behind every design choice in this doc: no MMU means no per-task isolation, but it also means no page tables to walk and no translation overhead on every memory access - one less source of "how long could this possibly take" in a system that has to answer that question.

3  The Task Control Block

Every fact the scheduler knows about a task lives in one struct - TCB_t, defined in tasks.c. It's small on purpose: a stack pointer, a couple of list links, a priority, a name.

Two of these are worth dwelling on. pxTopOfStack is a single pointer, yet it's the entire reason a context switch works at all - it's the address the next switch reads to know exactly where this task's registers were left. And xStateListItem is what makes "state" real: a task isn't Ready or Blocked because of a flag somewhere - it's Ready or Blocked because this list item is currently threaded into one linked list rather than another.

4  Task scheduling & scheduling queues

"Queue" here doesn't mean a FIFO - it means the actual data structure the scheduler walks to decide who runs next. FreeRTOS keeps one list per priority level, plus a separate list for anyone waiting on a timeout.

The actual scheduling event is almost anticlimactic: a tick interrupt or a task blocking/waking pends a switch, that switch calls vTaskSwitchContext(), and that function's whole job is "find the highest-priority non-empty entry in pxReadyTasksLists[] and make it pxCurrentTCB." How it finds that entry quickly is its own topic - the next section.

5  The scheduling algorithm

Fixed-priority preemptive, full stop. The highest-priority Ready task always runs. A priority-9 task makes zero progress while any priority-10 task is Ready - there's no fairness mechanism, and none is wanted. Tasks that share a priority round-robin between each other via time-slicing, if configUSE_TIME_SLICING is on.

Where the actual switch happens. None of this section moves a single register - it only decides which TCB becomes pxCurrentTCB. Loading that task's registers back onto the core is PendSV_Handler's job, not the scheduler's - covered in the SysTick / PendSV / SVC notes.
